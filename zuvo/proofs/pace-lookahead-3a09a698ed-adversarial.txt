FILE: src/claude_swap/autoswitch.py:3038
ID: autoswitch.py:3038:held-crossing-never-expires
ISSUE: A projected crossing is held indefinitely while the same reading stands — there is no staleness bound on the stored `projected` value.
ATTACK VECTOR: Readings normally change every 1–3 min, but the climb rate is measured once and then trusted forever. If the usage feed stalls, the window fills more slowly than measured, or the fleet simply stops burning quota after the rise (e.g., 24→57 measured, then utilization sits at 57 for 45 minutes), every subsequent tick still returns `projected >= threshold`, so the engine keeps forcing proactive switches based on a projection whose premise (the climb continues) has long stopped being true. The docstring says "held while that reading stands (a blocked switch keeps the crossing, like a real one)" — but a real threshold crossing is re-verified against fresh readings each tick; this one is verified against a measurement that ages without bound, so the "like a real one" claim does not hold for a reading that stands far past the normal 1–3 min cadence. In production this manifests as account churn / unnecessary switches during quiet periods after a burst.
SUGGESTED FIX: Cap how long a held crossing remains valid — e.g., store the projection's computed-at time and treat the crossing as expired once `now - since` exceeds some multiple of the normal reading cadence (or `lookahead` itself), resetting `_pace_sample` on expiry.

SEVERITY: WARNING
CONFIDENCE: medium
FILE: src/claude_swap/autoswitch.py:3028
ID: autoswitch.py:3028:short-elapsed-rate-extrapolation
ISSUE: The projection extrapolates `lookahead / elapsed` with no minimum on `elapsed`, so a small rise measured over a short interval is amplified into a huge projected value.
ATTACK VECTOR: `projected = utilization + (utilization - before) / elapsed * lookahead`. The setting spec allows `pace_lookahead_seconds` up to 3600 s. If two distinct readings happen to arrive close together — e.g., the daemon's tick coincides with the provider updating readings, or a delayed tick compresses the observed interval to ~15 s — then a mundane 1–2 point rise measured over 15 s with a 1800 s lookahead projects +120 to +240 points and fires a proactive switch on pure noise. The motivating incident (33 points over 151 s) is a 21x amplification; the code does nothing to distinguish that from a 1-point jitter amplified 240x. The test suite only exercises elapsed ≥ 60 s, so this failure mode is invisible to the author's tests.
SUGGESTED FIX: Require a minimum measurement window before trusting the rate — e.g., `if elapsed < 30: return False` (keep the sample, don't recompute the projection), or require the rise itself to exceed a noise floor (e.g., 2 points) before projecting.

SEVERITY: INFO
CONFIDENCE: low
FILE: src/claude_swap/autoswitch.py:3020
ID: autoswitch.py:3020:strict-drop-resets-baseline
ISSUE: Any strict decrease in utilization — even sub-point float jitter — resets the baseline and silently discards a held crossing.
ATTACK VECTOR: `utilization` is derived as `100.0 - base_h` (float headroom arithmetic). If the provider's headroom value wobbles slightly (95.0 → 94.9) due to rounding or in-flight request settlement rather than a true window reset, `utilization < sample[2]` wipes `_pace_sample`, including a legitimately held crossing, and detection needs two fresh distinct readings (2–6 minutes) to re-arm — exactly the blind window the feature exists to close. SUGGESTED FIX: Treat only drops larger than a small epsilon (e.g., 1–2 points) as a window reset; for smaller drops, keep the existing sample (optionally clamp `sample[2]` down to the new value).
