ISSUE: Missing `active_headroom is None` handling in prefer mode permanently deadlocks autoswitch on broken/unauthenticated primary accounts  
ATTACK VECTOR: When the primary account's credentials expire, get revoked (HTTP 401), hit rate limits without quota headers (HTTP 429), or encounter network failures, `active_headroom` is `None`. Lines 1770–1775 guard the deactivation of `pin_active` with `active_headroom is not None and 100.0 - active_headroom >= settings.threshold`, leaving `pin_active = True`. The engine then enters lines 1789–1798, resets `self._unhealthy_ticks = 0` and `self._home_unknown_since = None` (preventing timeouts or quarantine), emits a `NoSwitchEvent` falsely claiming `Account-{home} has quota and retains priority`, and unconditionally returns `TickOutcome.NO_ACTION`. The engine becomes permanently paralyzed on a non-functional primary account and never fails over to available backups.  
SUGGESTED FIX: Ensure that in prefer mode, missing headroom does not retain the pin or claim valid quota:
```python
        if (
            settings.home_mode == "prefer"
            and current == home
            and (active_headroom is None or 100.0 - active_headroom >= settings.threshold)
        ):
            pin_active = False
```
And only emit the priority retention `NoSwitchEvent` if `active_headroom is not None and 100.0 - active_headroom < settings.threshold`.

SEVERITY: CRITICAL  
CONFIDENCE: high  
FILE: src/claude_swap/usage_store.py:851  
ISSUE: Conflating failed poll attempts with successful observations permanently suppresses reset-based quota recovery  
ATTACK VECTOR: In `UsageStore.request_reset_poll`, line 851 checks `if attempted is not None and attempted >= reset: return`. When `now >= reset`, `nextPollAt` is moved to `now`. The engine attempts to poll the preferred account, which immediately sets `lastAttemptAt = now`. If this single attempt fails due to a transient issue (network glitch, socket timeout, HTTP 502/503/504, or HTTP 429 rate limit), `lastGood` and `fetchedAt` remain unupdated. On all subsequent ticks, `attempted >= reset` remains `True` forever. `request_reset_poll` permanently returns without ever accelerating polling again for that window, abandoning the account on fallbacks despite quota having recovered.  
SUGGESTED FIX: Do not suppress poll scheduling based on failed attempts alone. Only suppress if an observation succeeded (`fetched >= reset`) or if the account is currently in active backoff:
```python
            if fetched >= reset or reset > now:
                return
            if row.get("backoffUntil") and now < _num_or_none(row.get("backoffUntil"), 0):
                return
```
